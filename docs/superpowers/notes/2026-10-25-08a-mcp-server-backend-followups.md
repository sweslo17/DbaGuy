## Outcome against the pain points (feature-priorities §2, §3, §5, §8)

- §8 「AI：只做 MCP server」 and §3 S9 (the user's own request): delivered for the backend, on all five engines. Claude Code and any other MCP client can list and describe the schema of the connections the user shares, and run one read statement per call, through DbaGuy's own connection settings; nothing else (no chat, no explain or fix buttons, no resources or prompts, no writes, no OAuth, no stdio bridge). Seven tools: `list_connections`, `list_objects`, `search_objects`, `describe`, `run_query`, `explain`, `sample_fields` (Couchbase). It is not usable from the app until 08b (the switch and the token are in `settings.json` and the API).
- Q1 light and fast: with the switch off nothing of the SDK is imported (a test starts a fresh process and reads `sys.modules`) and the packaged app's startup did not move (cold start 0.97–1.05 s, first launch 2.33 s; `footprint` sum 169–175 MB; backend 81–83 MB; 06c: 1.00–1.04 s, 167–173, 80–81). With it on, the frozen sidecar listened 0.26–0.28 s after the switch (0.68 s right after a build; budget 1 s) and its RSS grew +22 MB (103–104 → 125–126 MB; budget 30 MB), 164–166 MB after calls on five engines. A call's memory is the response budget plus one page: a 100 MB value reads one row (traced peak 100 MB; RSS stays up because macOS's malloc keeps the block: 128 → 491–512 MB, flat over nine calls). `run_query` through MCP takes 2–9 ms with a session open (budget 100 ms). Disk: sidecar 48,192 → 63,176 KB (+14,984 KB), `.app` 77.76 → 92.26 MiB, JS +0.37 kB. What was stepped on: +22 MB while the server is on and +15 MB on disk for everyone; three more round trips per agent call; the per-row loop costs 2–5 µs a row on agent reads only (at most 5 ms for 1,000 rows); and, for everyone with a read-only MySQL connection, one more round trip per statement outside a transaction (ruling T7-1, below).
- Q2 never lose work: agents get sessions of their own and never touch a user's tab, transaction or staged edits; every call ends in ROLLBACK and releases session locks, and a frame that cannot end cleanly closes its session (the next call never meets a transaction or a lock the last one left); the call's deadline covers the lock, the session's opening and every page; a client's cancel stops the statement (0.02–0.27 s, both protocol versions); at most 16 call workers at once and 8 sessions; History keeps agents in their own 5,000-record cap so a loop cannot push out the user's 50,000; starting the server never delays the API (1 s after the app is up, on its own thread); stopping takes 0.12–0.19 s with clients connected. Stepped on: a read holds its locks up to 60 s (30 s on red connections): PostgreSQL's AccessShareLock and MySQL's metadata lock make a user's `ALTER` wait, SQLite's SHARED lock can make the user's own commit fail with `SQLITE_BUSY`. Documented, not removable.
- Q3 trustworthy (here: nothing an agent sends writes or acts beyond reading, and the user can see what it did): off by default, opened connection by connection; writes stop at the database on PostgreSQL, MySQL, SQLite and Couchbase (each tested with the gate taken out), and at the gate plus a rollback on SQL Server, which the connection says (`read_only_by: "dbaguy"`); the gate closes what a read-only transaction leaves open (server files and programs, other sessions, session locks, SQL run from text, MySQL `INTO` and executable comments); the login's dangerous privileges are read and shown; the token is a bearer token on 127.0.0.1 with Host and Origin checks; no dialog and no Keychain read when an agent calls (a locked connection says so); every call, refused ones included, goes to History with the client's name; nothing at INFO or above holds SQL, a value, a server's message or the token (an audit test). Adversarial reviews of the gate and the read path (about 145 pure inputs on five dialects, live checks, about 3,600 schema-tool fuzz calls, about 17,000 random read calls) found no write that got through; they found gaps that were closed: a deny-list that never ran for SQL Server's remote readers, a PostgreSQL login with `standard_conforming_strings` off, a MySQL `sql_mode` and `sql_select_limit` that blinded the guard, an unbounded page. It also found and fixed a hole in the **user's own** read-only MySQL tabs (a function flips the session to READ WRITE, then a ROLLBACK, then a function that writes: a row was written; D-08-5). Stepped on: the token sits in clear in Claude Code's `~/.claude.json`; the fixed port is open to another OS user while DbaGuy is closed; another login is the only complete protection against a user function that kills sessions or reads files; SQL Server cannot be made read-only by the server. All in CLAUDE.md's known limits.
- Q4 focus: seven tools and nothing else; no per-client permissions, no agent-only login field (the documented way is a duplicate connection with a read-only login, 08b).
- Q5 multi-engine: one tool set for five engines; engine facts live in `services/agent_gate.py`, the tables of `sql/dialects.py`, `adapters/mysql/read_only.py`, the adapters' `open(…, agent=)` and `login_privileges()`.
- Q6 macOS: backend only. The Settings API 08b needs is there (state, token, regenerate, the Claude Code commands as text). One macOS cost: a rebuilt app's first Keychain read of `mcp:token` can show the "allow access" prompt, like the passwords.
- §3 M2, M11, M12, M13: M2 layered exploration (`list_objects` → `describe`, search, no dump); M11 read-only at the database where the engine can, production (red) connections capped at 30 s; M12 timeouts, cancel and every limit (rows, cell, response, memory, time, `sql` length); M13 History for every call.
- §5 principles: 1 off by default and a global switch; 3 `schema` access reads no row; 4 server messages only in the tool result and DEBUG; 5 database-level read-only (SQL Server excepted and disclosed); 6 MCP only; 2 does not apply (DbaGuy calls no model).

## Company database checklist (dev ran PostgreSQL 17.11, MySQL 8.4.11, SQL Server 2022, SQLite 3.54.1 and Couchbase EE 7.6.12 only)

- **A10, MySQL 5.7** (`START TRANSACTION READ ONLY`, `max_execution_time`, `RELEASE_ALL_LOCKS()` from 5.7.5, the plain `EXPLAIN` where there is no `FORMAT=TREE`): MySQL before 5.7.8 and MariaDB are now refused when the agent session opens, so 5.7.8 and later are the ones to check. Also on 5.7.8–5.7.19: `transaction_read_only` does not exist, the guard falls back to `tx_read_only` (unit-tested only), and `transaction_isolation` is not set back there (`tx_isolation`); `show_create_table_verbosity` exists from 5.7.22 but is set back only from 8.0.11 (final-review list). Confirm the `_MYSQL_RESET` statement runs for the company login (every variable it sets must be settable without SESSION_VARIABLES_ADMIN), and what a server that passes the version rule but is not MySQL (TiDB, Aurora) does with it.
- **A12, MySQL FILE with `secure_file_priv`**: a login with FILE: `list_connections` shows `file` and the directory (or "any directory"); the gate refuses `INTO` and `LOAD_FILE` in any case. Dev has no login with FILE that writes; root can only write under `secure_file_priv`.
- **PostgreSQL 12 and 13**: `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program` and `pg_signal_backend` exist from PostgreSQL 11; the login read queries them and `has_function_privilege` on the file functions. On PostgreSQL before 11 the query fails (one WARNING a minute at most, `login` stays null). Also: a role or database with `standard_conforming_strings = off` (the agent call is refused with a message; grid editing is already read-only for such a server, ⑤ G3), and the single-row streaming on the company's version (psycopg's `stream`, no `DECLARE`).
- **SQL Server without SHOWPLAN permission** (A8's second half): `explain` on a login that may not `SET SHOWPLAN_TEXT ON`: the error text and that the session is still usable. Also SQL Server 2016, 2017 and Azure SQL: `HAS_PERMS_BY_NAME`, `sys.user_token` and `sys.database_permissions` in the login read.
- **A login without `db_owner`**: the privileges read for a `db_datareader`-only login says "nothing beyond reading"; a login with INSERT on one table, or EXECUTE on a schema, or membership in a role that has them, says `can_write` (live-checked on SQL Server 2022 with about 30 scratch logins; nothing older). For PostgreSQL a role with only a direct `pg_read_file` grant reports `server_files_read`.
- **Couchbase with a restricted login** (no `query_system_catalog`): `describe` shows `indexes: []` without the tree's "may need query_system_catalog" hint; `sample_fields` and `run_query` need the keyspace's data read role; `ADVISE` is not offered. Run the tools with `dbaguy_reader`-like roles on the company cluster.
- **A connection through an SSH tunnel** and a slow link: agent sessions use the same opener as tabs; never exercised for MCP. A call's deadline counts from the lock, the connection's opening and the frame (4 to 8 round trips on MySQL), so a slow link eats into 30 s.
- **Production (red) connections**: the 30 s cap and its note; `read_only_by` and the login list for the real production login.
- **A real database with big values and wide tables**: `run_query` against a table with 1 MB cells, a 1,500-column view, a table with many `json` columns; the response stays under 40,000 characters and the sidecar's RSS comes back after the call (or stays at its malloc-cached level).
